## 本次要提的 PR

- 目标仓库：`https://github.com/awesome-dsh-plugin/awesome-dsh-plugin`
- 只加**一个文件**：`data/plugins/Orliba__dsh-ratchet.yml`
- 文件内容 = 本目录的 `awesome-dsh-plugin__Orliba__dsh-ratchet.yml`（已用宿主的 yaml 解析器验过：`url`/`name`/`category`/`description.en`/`description.zh` 五个字段，两条描述都以句号结尾）
- PR 正文 = 本目录的 `PR-body.md`
- 分类选 `workflow`（工作流与自动化）。分类选偏了维护者会直接改，不会打回。

## 规则要点（提 PR 前容易踩的）

1. **只加一个文件，绝不手改 README**。两个 README 由 `scripts/generate-readme.mjs` 从 `data/plugins/*.yml` 生成，手改必冲突。
2. **一个 PR 最多 3 条**。
3. **描述里含 `: `（冒号加空格）必须加引号**，否则 YAML 当成嵌套键。我们的两条描述都已用单引号包住。
4. **描述必须属实**，会被拿代码核对；提到命令或 API 就必须真存在。这是唯一会让「本来不错的插件」被打回的原因。我们的描述里每个说法都能对上代码（工具名、`/ratchet`、六个设置字段、会话投影、三个校验器）。
5. **不要写 `npm:` 字段**，市场从 registry 自动采集，手写会被校验拒绝。
6. 仓库要带 `dsh-plugin` topic。
7. PR 通过只是**前置条件**，维护者会真的读仓库再合并。需要改时会给 PR 打 `held: author` 标签 —— 那不是拒绝，把修改推到同一分支 + 留**一条**评论说明改了什么即可，别反复推送。

## 为什么这一步之前没做

npm 只是「包能被装上」，市场是「别人能搜到」。这两件事没有依赖关系，`dsh-ratchet@0.2.0` 发布成功并不代表已上架 —— 之前只发了 npm，列表这一条一直是空的。查过 `plugins.json`（10778 条），里面确实只有 `Orliba/dsh-context-keeper`，没有 `dsh-ratchet`。
